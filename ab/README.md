# A/B 하네스

출하된 리팩터 파이프라인(A)과 주소 기반 프로토타입(B)을 같은 입력으로 돌려 비교한다.
`wigtn-tech-report`의 WIGSS 리포트가 인용하는 수치가 전부 여기서 나온다.

```bash
pnpm test:ab
```

결과는 `ab/results.md`, `ab/exp2.md`, `ab/exp3.md`와 같은 이름의 `.json`으로 다시 쓰인다.
커밋된 파일은 리포트가 인용한 실행 결과이므로, 재실행 후 값이 달라지면 그 변화 자체가 신호다.

## 무엇을 비교하는가

|            | A · 출하 v0.2.0                      | B · 프로토타입                    |
| ---------- | ------------------------------------ | --------------------------------- |
| 조인       | className 문자열을 전체 소스에서 검색 | 주소(file:line:col)로 직접 해석    |
| 번역       | 브레이크포인트 접두사를 보지 않음     | 활성 브레이크포인트 토큰만 조작    |
| 출력       | 인라인 스타일 폴백 허용               | 컨벤션 린터 통과 필수, 불가 시 포기 |
| 적용       | `content.indexOf(original)`          | 문자 범위 splice                  |

A는 **재구현이 아니다.** `generateRefactorResult()`를 그대로 호출하므로
`refactor-client → intent-adapter → dispatcher → rewriters` 전체가 실제로 돈다.

두 쪽은 px↔Tailwind 스케일 표(`pxToTw`)와 `/api/apply`의 안전 가드를 **공유한다.**
비교 대상은 조인·번역·출력 정책이지 스케일 표가 아니다.

## 구성

```
ab/
  fixtures/          실제 React·Tailwind 코드에서 흔한 10가지 패턴
  scenarios.ts       각 픽스처의 편집 대상 주소, 제스처, 활성 브레이크포인트, 기대 결과
  util.ts            소스 로딩, 채점, 오염 검사, 두 가지 apply 구현
  versionA.ts        출하 파이프라인 호출
  versionB.ts        주소 해석 + 브레이크포인트 인식 편집 + 컨벤션 린터
  run.test.ts        실험 1 — 패턴 처리 정확도
  exp2.test.ts       실험 2 — 중복 밀도 vs 조인 정확도 (N = 1..32)
  exp3.test.ts       실험 3 — 저장 1회 수집 비용, 롤백 안전성
  vitest.config.ts   기본 스위트와 분리된 설정
```

### 픽스처

파일 간 className 충돌은 **의도적으로 제거했다.** 패턴 처리와 중복 밀도를 한 번에 재면
두 효과가 섞이기 때문이다. 중복의 영향은 실험 2가 따로 측정한다.

`S2_duplicate.tsx`와 `S8_move.tsx`는 파일 **안**의 중복을 일부러 유지한다. 각각
동일한 카드 둘, 동일한 사이드바 링크 둘이며 그게 그 시나리오의 요점이다.

### 채점

정확도는 편집 후 대상 주소의 **정적 className**을 기대값과 비교한다
(`util.ts:staticClassAt`). 문자열 리터럴이면 값 그대로, 템플릿 리터럴이면 정적 조각,
`cn()`이면 첫 문자열 인자를 본다. A와 B에 같은 채점기를 쓴다.

오염은 대상 요소가 아니라 **파일 전체**를 before/after로 비교해 센다
(`util.ts:filePollution`). 엉뚱한 요소를 고쳤어도 남은 임의값과 중복 토큰은 오염이다.

## 결과 요약

`pnpm test:ab` 실행 시점 기준이며, 자세한 값은 각 `.md`에 있다.

| 지표                      | A          | B          |
| ------------------------- | ---------- | ---------- |
| 패턴 10종 정확도          | 5/10       | 10/10      |
| 오편집 (썼는데 틀림)      | 3          | 0          |
| 중복 32개일 때 조인 정확도 | 3% (1/N)   | 100%       |
| 저장 1회 읽기             | 40 파일 · 162,606 B | 1 파일 · 284 B |
| 롤백 시 사용자 동시 수정  | 소실       | 보존       |

## 하네스가 찾아낸 것

설계 메모에는 없던 항목이다. **B의 첫 구현은 주소로 올바른 요소를 찾고도
S2와 S8에서 A와 똑같이 실패했다.** 원인은 `CodeDiff`가 `original`/`modified`
문자열 쌍만 담고, apply가 `indexOf`로 위치를 다시 찾는 데 있었다. 그 순간 주소가
버려지고 중복 모호성이 되살아난다.

`util.ts:applyByRange`로 문자 범위를 apply까지 전달하자 두 시나리오가 통과했다.
`TargetLocation.range` 타입은 이미 존재하며, `dispatcher.ts`가
`{ start: 0, end: 0 }` 플레이스홀더를 넘기면서 "Phase 3+ locators will produce
real ranges"라는 주석을 달아둔 그 자리다.

## 한계

- 픽스처 10개는 특정 코드 형태를 시험하려고 고른 것이지 어떤 저장소의 표본도 아니다.
  각 결함이 발생한다는 것과 어떻게 발생하는지를 보일 뿐, 빈도는 말하지 않는다.
- `5/10`은 이 픽스처 집합에 한정된다. 파일 간 충돌을 제거하기 전에는 2/10이었다.
- B는 해석·브레이크포인트 편집·범위 적용 세 축만 구현한다. 구조 편집, 모델 폴백,
  편집 표면은 없다.
- 지연은 한 대의 기계에서 프로세스 안에서 측정했고, 현재 저장 흐름이 쓰기 뒤에 붙이는
  고정 지연(1.0s / 3.0s / 4.5s)은 빠져 있다.
- 실험 3의 롤백은 문서화된 복원 동작의 시뮬레이션이다. 다만 모사한 경로는 파일을
  저장 직전 내용으로 다시 쓰는 호출 하나다.

## 이 하네스가 유지되어야 하는 이유

리라이터나 apply 경로를 고칠 때 회귀를 잡는다. 지금은 A가 5/10이지만, 결함을
고칠 때마다 이 숫자가 올라가야 하고 올라가지 않으면 고쳐지지 않은 것이다.

실제 프로젝트를 커밋 해시로 고정한 골든 벤치마크로 확장하는 것이 다음 단계다.
그때까지 이 하네스는 벤치마크가 아니라 **결함 재현 장치**다.
